# Construindo um Banco de Dados Key-Value de Alta Performance em Go

Nos últimos meses, embarquei em um desafio técnico fascinante: construir do zero um banco de dados key-value de alta performance chamado **Escabelo**. O projeto nasceu de um desafio da Pizzaria Bate-Papo e se transformou em uma implementação completa de LSM-tree (Log-Structured Merge-Tree), similar ao que você encontra em sistemas como RocksDB e LevelDB.

## O Desafio

O objetivo era criar um sistema capaz de:

- **Alta taxa de escrita**: Prioridade máxima para operações de write
- **Leitura eficiente**: Otimizado para padrão de acesso 80/20 (80% das consultas em 20% dos dados)
- **Persistência garantida**: Zero perda de dados após confirmação de escrita
- **Eficiência de armazenamento**: Overhead menor que 15%
- **Protocolo TCP customizado**: Interface simples e debugável

### Requisitos Técnicos

O desafio especificava workloads realistas:
- 70% chaves pequenas (≤ 1KB)
- 20% chaves médias (1KB - 10KB)
- 10% chaves grandes (10KB - 100KB)
- Padrão de acesso 80/20 (hot/cold keys)

## Por Que LSM-Tree?

A primeira decisão crítica foi escolher a arquitetura de armazenamento. Após analisar as alternativas, optei por **LSM-tree** pelos seguintes motivos:

### Vantagens para Write-Heavy Workloads

**B-Trees** (usadas em bancos relacionais) são excelentes para leituras, mas sofrem com escritas aleatórias no disco. Cada write pode resultar em múltiplas operações de I/O para manter a árvore balanceada.

**LSM-Trees**, por outro lado, transformam escritas aleatórias em escritas sequenciais:

1. Todas as escritas vão primeiro para memória (MemTable)
2. Quando a memória enche, os dados são escritos sequencialmente em disco (SSTable)
3. Periodicamente, arquivos são mesclados para otimizar leituras

**Resultado**: Escritas sequenciais são 100-1000x mais rápidas que aleatórias em SSDs e HDDs.

## Arquitetura do Sistema

### Visão Geral

```
Cliente (TCP)
    ↓
Servidor TCP (Parser + Handler)
    ↓
Storage Engine
    ├── MemTable (Active) → Hash Map O(1)
    ├── Immutable MemTables → Fila de Flush
    ├── SST Files → Arquivos imutáveis ordenados
    ├── Compactor → Background worker
    └── WAL → Write-Ahead Log
```

### Componentes Principais

#### 1. MemTable - O Coração do Sistema

A MemTable é uma estrutura in-memory que recebe todas as escritas:

```go
type MemTable struct {
    mu      sync.RWMutex
    data    map[string]*Entry  // Hash map para O(1)
    size    int64              // Tracking de tamanho
    maxSize int64              // Limite para flush
}
```

**Por que Hash Map?**
- **Simplicidade**: Implementação nativa do Go
- **Performance**: O(1) para reads e writes
- **Trade-off consciente**: Sacrifico ordem em memória (preciso ordenar no flush) por velocidade absoluta

#### 2. Write-Ahead Log (WAL) - Garantindo Durabilidade

O WAL é o guardião da durabilidade. Antes de qualquer dado ser modificado na MemTable, ele é escrito no log:

```go
// Formato binário eficiente
Entry: [opType:1][timestamp:8][keyLen:4][key:N][valueLen:4][value:M]
```

**Processo de Escrita**:
1. Cliente envia `write user:123|John Doe`
2. Append no WAL (durabilidade)
3. Write na MemTable (velocidade)
4. Retorna `success` ao cliente

**Crash Recovery**:
Se o servidor cair, ao reiniciar:
1. Lê o WAL do início
2. Replaya todas as operações na MemTable
3. Estado consistente restaurado

**Otimização**: Buffer de 256KB com flush apenas quando quase cheio, reduzindo syscalls de I/O.

#### 3. SSTables - Persistência Eficiente

Quando a MemTable atinge 64MB (configurável), ela é "congelada" e uma nova MemTable ativa é criada. A MemTable congelada é então escrita em disco como SSTable:

**Características**:
- **Imutável**: Nunca modificado após criação
- **Ordenado**: Chaves em ordem lexicográfica
- **Indexado**: Índice esparso (1 em cada 10 chaves)

**Índice Esparso**:
```
Keys:     a  b  c  d  e  f  g  h  i  j  k  l
Index:    ^           ^           ^
         a=0         e=40        i=80
```

Isso reduz uso de memória em 90% com impacto mínimo em performance de leitura.

#### 4. Compactor - Mantendo Performance

Com o tempo, múltiplos SSTables se acumulam. O Compactor roda em background (default: 5 minutos) e:

1. **Seleciona** os 4 SSTables mais antigos
2. **Mescla** todas as entradas
3. **Mantém** apenas a versão mais recente de cada chave
4. **Remove** tombstones (chaves deletadas)
5. **Escreve** SSTable mesclado
6. **Deleta** SSTables antigos

**Benefícios**:
- Reduz amplificação de leitura (menos arquivos para verificar)
- Reclama espaço de dados deletados
- Melhora performance geral

## Fluxos de Operação

### Write Path - Otimizado para Velocidade

```
1. Cliente: "write user:123|John Doe\r"
2. TCP Parser valida comando
3. Engine.Put()
   ├─→ WAL.Append() [Durabilidade]
   └─→ MemTable.Put() [Velocidade]
4. Check: MemTable cheia?
   ├─→ Não: Retorna "success" (~1ms)
   └─→ Sim: 
       ├─→ Congela MemTable atual
       ├─→ Cria nova MemTable
       └─→ Trigger Flush assíncrono
```

**Latência típica**: 1-2ms (incluindo WAL sync)

### Read Path - Otimizado para Hot Keys

```
1. Cliente: "read user:123\r"
2. Engine.Get()
   ├─→ MemTable.Get() [O(1)]
   │   └─→ Encontrado? → Retorna (~0.1ms)
   ├─→ Immutable MemTables [O(1) cada]
   │   └─→ Encontrado? → Retorna (~0.2ms)
   └─→ SST Files [O(log n) com índice esparso]
       └─→ Encontrado? → Retorna (~1-5ms)
```

**Padrão 80/20**: 80% das leituras (hot keys) vêm da MemTable em menos de 1ms!

### Delete Path - Tombstones

Deleções usam o padrão **tombstone**:

```go
func (m *MemTable) Delete(key string) {
    entry.Deleted = true
    entry.Timestamp = time.Now().UnixNano()
}
```

A deleção física só ocorre na compactação, mantendo writes rápidos.

## Decisões de Design e Trade-offs

### 1. Protocolo Textual vs Binário

**Decisão**: Protocolo baseado em texto com separador `\r`

**Razões**:
- ✅ Debugável com telnet/netcat
- ✅ Parser trivial
- ✅ Qualquer linguagem pode implementar cliente
- ❌ Menos eficiente que binário (~10% overhead)

**Veredicto**: Vale a pena. A facilidade de debug e integração supera o overhead.

### 2. Hash Map vs Skip List para MemTable

**Decisão**: Hash Map (`map[string]*Entry`)

**Razões**:
- ✅ O(1) garantido para reads/writes
- ✅ Implementação nativa do Go
- ❌ Precisa ordenar no flush

**Alternativa**: Skip List mantém ordem, mas é O(log n) e mais complexo.

**Veredicto**: Para MemTables de 64MB, ordenar no flush (operação rara) é aceitável.

### 3. Compactação Simples vs Leveled

**Decisão**: Compactação simples (mesclar 4 SSTables mais antigos)

**Razões**:
- ✅ Simples de implementar e debugar
- ✅ Comportamento previsível
- ✅ Suficiente para workloads do desafio

**Alternativa**: Leveled Compaction (LevelDB) é mais sofisticado mas complexo.

**Veredicto**: Começar simples. Leveled compaction pode ser adicionado depois.

## Otimizações Implementadas

### 1. WAL Group Commit

**Problema**: Flush síncrono em cada write matava performance.

**Solução**: Buffer de 256KB, flush apenas quando >252KB cheio.

```go
if w.writer.Buffered() >= w.bufSize-4096 {
    return w.writer.Flush()
}
```

**Resultado**: Redução de syscalls de I/O, permite batching natural.

### 2. Lock Contention Reduction

**Problema**: Stats lock aninhado dentro de engine lock causava contenção.

**Solução**: Atualizar stats fora do engine lock.

```go
// Write to memtable
e.mu.Lock()
e.memtable.Put(key, value)
e.mu.Unlock()

// Update stats outside lock
e.stats.mu.Lock()
e.stats.Writes++
e.stats.mu.Unlock()
```

**Resultado**: ~30% redução em tempo de lock holding.

### 3. TCP Buffer Optimization

**Problema**: Buffers padrão de 4KB causavam muitos syscalls.

**Solução**: Buffers de 64KB para read e write.

```go
reader := bufio.NewReaderSize(conn, 64*1024)
writer := bufio.NewWriterSize(conn, 64*1024)
```

**Resultado**: Redução significativa em syscalls de rede.

## Performance Alcançada

### Benchmarks Reais

Com configuração balanceada (64MB MemTable, 5min compaction):

```
Write Throughput:  4,600-5,100 ops/s
Read Throughput:   7,000-7,300 ops/s
Delete Throughput: 3,600-5,600 ops/s

Latência P95:
  Write: menos de 10ms
  Read:  menos de 5ms (hot keys menos de 1ms)
```

### Workload 80/20

O benchmark simula padrão realista:
- 80% das requisições em 20% das chaves (hot keys)
- Distribuição de tamanhos: 70/20/10
- Mix configurável de read/write

**Resultado**: Hot keys ficam em memória, cold keys em disco - exatamente como esperado!

## Concorrência e Thread Safety

### Modelo de Concorrência

```go
// MemTable: RWMutex (read-heavy optimization)
type MemTable struct {
    mu sync.RWMutex
    // ...
}

// WAL: Mutex (sequential writes)
type WAL struct {
    mu sync.Mutex
    // ...
}
```

### Background Workers

Três goroutines rodam em background:

1. **Flusher**: Escreve immutable memtables para SST
2. **WAL Syncer**: Sync periódico do WAL para disco
3. **Compactor**: Mescla SSTables

Todos não-bloqueantes, permitindo operações concorrentes.

## Crash Recovery - Testado na Prática

### Teste 1: Kill -9 Durante Writes

```bash
# Escrever dados
write test:1|data1
write test:2|data2

# Kill -9 no servidor
kill -9 $PID

# Reiniciar
./bin/escabelo

# Verificar
read test:1  → data1 ✅
read test:2  → data2 ✅
```

**Resultado**: Zero perda de dados (dentro do intervalo de WAL sync).

### Teste 2: Compaction Durante Crash

Compactação é não-destrutiva:
1. Escreve novo SSTable
2. Só então deleta antigos

**Resultado**: Estado sempre consistente.

## Lições Aprendidas

### 1. Simplicidade é Poder

Comecei com ideias complexas (leveled compaction, bloom filters, block cache). Implementar o básico primeiro foi crucial:
- Entender trade-offs reais
- Debugar problemas fundamentais
- Medir antes de otimizar

### 2. Write Amplification é Real

Cada escrita é multiplicada:
- 1x WAL
- 1x MemTable (memória)
- 1x SST Flush
- 0.25x Compaction (média)

**Total**: ~2.25x write amplification

Isso é aceitável para workloads write-heavy, mas importante monitorar.

### 3. Testes de Crash São Essenciais

Simular crashes (kill -9) revelou bugs sutis:
- WAL não sincronizado
- SST parcialmente escrito
- Estado inconsistente após recovery

**Solução**: Testes automatizados de crash recovery.

### 4. Go é Excelente para Databases

**Pontos Fortes**:
- Goroutines para background workers
- Garbage collector elimina bugs de memória
- Performance próxima de C++ para I/O bound
- Tooling excelente (pprof, race detector)

**Pontos Fracos**:
- GC pode causar latency spikes (mitigável)
- Menos controle sobre layout de memória

## Próximos Passos

### Alta Prioridade

1. **Bloom Filters**: Reduzir 50-70% de disk I/O para keys inexistentes
2. **Leveled Compaction**: Melhor space amplification
3. **Batch Write API**: 2-3x throughput em writes

### Média Prioridade

4. **Block Cache**: LRU cache de 128MB para blocos SST
5. **Compression**: Snappy/LZ4 para reduzir espaço
6. **Parallel Compaction**: Utilizar múltiplos cores
